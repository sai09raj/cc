# Magnetic Rainstorm Mistake Register

## Purpose

This register records specific failure modes encountered across the Task 01–04 authoring cycles. It is deliberately concrete so another agent can recognize the symptom before repeating the cost.

| 65 | Shipped rubric criteria that bundle independently-reachable facts into one binary pass/fail | An external reviewer failed an unrelated task's rubric (verdict: "Fail — 20%+ Moderate Rubric Errors," 17/50 = 34%) specifically for criteria that fuse a mechanism description with an exact trace-file value whose correctness depends on the whole system, or that pack several unrelated checks into one AND-clause. Auditing QUORUM-7 and LEDGER-8 by the same standard — but verified by actually running each task's own real mutants, not just reading the text — found both tasks had it: LEDGER-8's old #20/#21 (bundling 4 and 3 accounts respectively) split cleanly under real mutants (e.g. omitting E4 alone left the trade pair wrong while the loan pair, driven by a different elimination entry, stayed correct); QUORUM-7's #16–18 and #21–28 (bundling 2–4 observations per row/subset) split the same way under 3 of 3 non-canonical mutants tested, affecting roughly 60% of that rubric's total weight. | A bundled criterion loses its full weight when only one of its sub-facts is wrong, so a submission that fixed 3 of 4 bundled facts scores identically to one that fixed 0 of 4 on that criterion — this is exactly the "moderate rubric error" pattern that produces a hard Fail verdict from a strict reviewer, independent of whether the task's actual engine/pilot scores look fine. | When drafting any criterion that names 2+ accounts/values/sub-facts together, ask whether a plausible single bug could make one true and another false; if yes, split into separate criteria before first submission — don't wait for a linter or reviewer to catch it. | 66 | Left the trace-integrity hash's serialization format underspecified in the packet, making the highest-weighted criterion unwinnable by guesswork | Two real LEDGER-8 pilots scored 94% and 92% — both models computed every dollar value correctly (matching the reference exactly) and both auditors correctly rejected both adversarial mutations, yet neither matched the certification hash (+8, the single highest-weighted criterion) — and the two pilots didn't even match each other's hash. | 67 | Trusted a cascading/amplifying dependency structure as sufficient difficulty on its own | TYPECHAIN-9 (Hindley-Milner type inference, one global substitution threaded through 27 chained bindings) was built specifically so a dropped generalization-exclusion rule would corrupt 23/27 bindings, confirmed at 17.7% under the real synthetic mutant — well under the 33% target. This task's entire difficulty hinged on one clearly-flagged, mechanically simple predicate (the eligibility rule) stated unambiguously everywhere on purpose (per mistake #66's own lesson) — so a careful frontier model just read it and implemented it correctly, and the cascade never triggered because the root-cause bug never happened. Making a spec maximally unambiguous, the right thing to do for fair grading, can remove the only source of difficulty when the underlying task has just one clean deviation point. | Before committing to a cascading-structure task design, ask not just "does a dropped rule corrupt most of the output" (amplification) but "how many genuinely distinct, interacting rules does a careful model have to get right, and is any single one of them subtle enough that a strong model has a real chance of missing it even when the spec is unambiguous" (base-rate of the triggering mistake). | 68 | Picked a mechanism whose facts are structurally independent, then tried to fix it by reweighting | STATIC10 (task10, static timing analysis on a digital circuit) built a correct reference engine, independent verifier, and 14-arc fixed circuit across four timing-exception regimes, intended to avoid TYPECHAIN-9's single-deviation-point problem via many genuinely different interacting rules. All five required single-bug mutants scored 40-66% against every reweighting attempted, never clearing the 33% target. | Worked the algebra explicitly: synchronous digital timing analysis deliberately breaks combinational dependency into independent per-stage arcs (that is what registers are *for*), so a narrow single-regime bug (e.g. one false-path misclassification) has no natural channel to corrupt any other arc. The certificate hash caught every mutant (maximally sensitive) but is capped at +10 like any other criterion, and no fair reweighting can make +10 outweigh the 70-90 points of content a narrow bug honestly leaves untouched without either violating the platform's +-10-per-criterion cap or assigning one arc 15-20x the weight of its siblings — not a rubric fix, just hidden difficulty-manufacturing. Same root cause as LEDGER-8's original failure (independent facts), this time caught at the design/S08 stage before any rubric or platform text existed, instead of after a real pilot. | Before investing in a full reference engine, ask whether the domain has *genuine* cross-item dependency (a later fact's correctness requires an earlier fact to already be correct — type-substitution threading, protocol state over time, running numeric integration) or is merely "many different rules applied to many independent items." ## Do

- Start with task architecture and semantic sufficiency.
- Run the perfect-semantics ablation before coding the oracle.
- Treat the artifact as an executable contract.
- Trace every oracle branch to a visible rule.
- Ask an independent reviewer to reconstruct semantics without reference code.
- Test rival interpretations and mutants.
- Validate the runtime before authoring around it.
- Generate prompt/rubric literals from canonical data.
- Keep criteria short, observable, and atomic.
- Compare model runs at the semantic level.
- Reconstruct and replay one pilot implementation before launching a batch.
- Find the earliest production divergence and map it to a visible rule.
- Calculate the plausible-wrong survival ceiling before platform entry.
- Apply the most generous valid score before selecting preferred runs.
- Archive exact scores, trajectories, frozen hashes, and grading sheets immediately.
- Record flaws candidly even after achieving the target score.
- Keep the submitted artifact free of internal paths, draft labels, audit notes, generator notes, and private workflow commentary unless the platform requires disclosure; never remove attribution that policy requires.
- Scan every positive criterion for a bundled prohibition ("must never," "not automatic") during initial authoring, not only after the linter flags it.
- Grade every numeric fact against the external reference value; never grade a model's own verifier's agreement with its own primary as if it were correctness.
- When a linter flags two criteria as contradictory, check whether they are two distinct correct answers sharing every dimension but one before rewriting anything.
- Treat metadata/vector-data stripping on any visual or graphical artifact as a correctness gate, verified at the raw-byte level: unremoved metadata or vector coordinates can hand the model the solution directly, and the task will not score below 50% no matter how sound the rubric is.
- Keep every rubric criterion body at 301 characters or fewer, and re-run the atomicity/self-containment check over every criterion after every edit round, not only at first drafting.
- Before first submission, run every real mutant already built for the score-topology audit against each criterion that names 2+ accounts/values/sub-facts, and split any criterion whose bundled sub-facts actually diverge independently under a real bug; don't rely on eyeballing the text alone.
- Before trusting any hash/certificate criterion's weight, verify the packet pins down every formatting degree of freedom (exact field names given verbatim, a literal header string, explicit zero/empty-value inclusion, exact separators, a fake-number worked example) — a synthetic mutant audit cannot catch this, since every mutant still follows the reference's own serialization convention; only a real, independently-reasoning pilot exposes it.
- When a cascading/amplifying design hinges on one isolated deviation point, ask how likely a careful frontier model is to actually make that specific mistake, not just how badly the output breaks if it does; an unambiguously-stated single rule can be amplification with nothing to amplify.
- Before writing the full reference engine for a "many interacting rules" design, confirm analytically that a later fact's formula actually consumes an earlier fact's computed value (genuine state-threading), not just that many different rules apply to many independent items; the latter cannot pass the S08 gate through reweighting alone.
- State every rounding/formatting rule's exact display width with a literal example, not just "N decimal places" -- a synthetic mutant audit cannot catch this, since the reference's own mutants all share its own formatting convention; only a real or blind-piloted solver exposes it.
- Before shipping, verify every sentence in packet prose that asserts a *consequence* of the stated rules (not a rule itself) against the reference engine's actual executed trace -- these are the sentences most likely written from intuition rather than execution, and most likely to go stale after a later constant tweak.
- Count the policy micro-rules that select among competing candidates or entities (eligibility, arbitration, tie-breaks, timers) before committing to an architecture; a handful of arithmetic update formulas is transcription, however much state they thread.
- Run an `opus`-alias local blind pilot as an early difficulty gate, before the rubric and platform package exist, and treat one clean content solve as an architecture failure.
- Trace every rubric criterion back to a prompt or artifact clause (reverse coverage), so no criterion grades something the solver was never asked to do.
- After entering the rubric on the platform, compare every row with the local file (numbers, coordinates, scenario labels and parameters); a dropped digit or a row copied from its neighbour fails correct answers.
- For every conditional rule in the prompt ("only when", "only if"), write a negative criterion that fires on exactly that violation, judged from the run's own reported values.

## Don’t

- Do not assume more edge cases rescue a small clean-rewrite task.
- Do not equate internal oracle agreement with source completeness.
- Do not accept private intent as a task rule.
- Do not treat shared rival outputs as independent mistakes.
- Do not force scores down through exact wording, hidden schemas, or narrow tolerances.
- Do not use intent language in binary criteria.
- Do not write a negative criterion that describes correct behavior.
- Do not rely on file existence without content checks.
- Do not type hashes, tuples, or checkpoints from memory.
- Do not promise a toolchain works until a smoke test succeeds.
- Do not launch six long runs before one pilot and convergence audit.
- Do not use an average below 50 when any required individual run is at or above 50.
- Do not let locally correct scaffolding carry a globally wrong production execution over the threshold.
- Do not build the difficulty plan around hoping a frontier model misunderstands one visible semantic.
- Do not submit merely because the score gate is met.
- Do not reword a criterion to chase a partial-tuple-overlap false positive; mark it invalid with the shared/differing dimensions named instead.
- Do not treat synthetic mutant scores as the acceptance gate; run real pilots and treat their scores as the actual evidence.
- Do not bundle two or more independently-achievable facts (two accounts, two trace values, a mechanism description plus a value, two unrelated mutation-rejection checks) into one binary criterion; a submission that gets half of it right still loses the whole weight.
- Do not describe a hash/certificate's serialization with prose like "sorted by account name" or "preceded by a header line" — give the literal field list, literal header string, and zero-inclusion rule verbatim, or a correct model will guess a different, equally defensible format and lose the criterion for a reason that has nothing to do with task correctness.
- Do not treat a cascading/amplifying dependency structure as difficulty by itself; if the whole design rests on one clearly-flagged, mechanically simple deviation point, a careful frontier model can just read and implement it correctly and the cascade never triggers.
- Do not pick a mechanism with structurally independent facts (each item's correctness derived only from its own data, not from any other item's value) and expect reweighting to manufacture cascading difficulty; a single capped-at-10 criterion cannot outweigh the content a narrow bug honestly leaves untouched, no matter how it's distributed.
- Do not publish the full rule set as one numbered, ordered list; that list is the perfect-semantics summary, and handing it over removes the composition work the task is supposed to test.
- Do not keep fixing packaging bugs after a clean blind-pilot content solve; Gate 8.5 means redesign, not another round.
- Do not write validity-only or presence-only criteria ("reports a bound not above the minimum", "reports a count for each scenario") when the prompt asks for the best value or a correct value; reviewers mark them slightly broad because a trivial answer passes.

## Five-minute review before any irreversible step

1. What is the exact visible source for the behavior I am about to grade?
2. Could a competent rival interpretation produce a different but valid result?
3. Am I copying a canonical value or retyping it?
4. Is this failure technical, environmental, cosmetic, or rubric-created?
5. Would I still call the task valid if the model’s answer were written by another human expert?

If any answer is uncomfortable, stop and audit before proceeding.
